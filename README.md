# mala-clock-liff

麻的小辛辣打卡系統 LINE 化（LIFF）的**獨立**工作區。

⚠ 與現有打卡系統 `~/mala-clock-in` **完全分離**，不共用任何資料、後端或儲存空間。

---

## 階段 0：可行性驗證 — ✅ 已完成（2026-08-27）

唯一的未知數是「LIFF 內建瀏覽器能不能穩定取得足夠精準的 GPS」。
`spike/gps-test.html` 就是回答這個問題的測試頁（純前端、零網路請求）。

### 實測結果（新竹光復店店內，iOS · LINE 26.12.1）

| 指標 | 實測 | 門檻 | 判定 |
|---|---|---|---|
| 精準度中位數 | **±13m** | ≤40m | ✅ 大幅優於門檻 |
| 最佳精準度 | ±8m | — | ✅ |
| 最差精準度 | ±1414m | ≤100m | ⚠ 首次粗定位，見下 |
| 最慢耗時 | 7,140ms | ≤8,000ms | ⚠ 過關但不寬裕 |
| LIFF init | 成功 | — | ✅ |
| 取樣次數 | 40 | — | — |

**結論：可行。**

- ±1414m 是**首次粗定位**（基地台／WiFi 定位，GPS 未鎖定時的初值）。
  正式系統「精準度 <40m 才送出，否則重抓最多 8 秒」的邏輯本來就會跳過它。
  測試頁的判定式只看最差值，所以顯示「勉強」——實際結論是通過。
- **7.1 秒冷啟動要處理**：正式版應在**頁面載入時就開始抓定位**（不等按鈕），
  同仁從點圖文選單到按下打卡的 2～3 秒足夠 GPS 鎖定，按下去就是瞬間完成。

### 一併驗證通過的項目

- LIFF 身分層設定：`liff.init()` 成功、scope 為 `["openid","profile"]`（`getProfile()` 拿得到 userId）
- 距離計算（haversine）：7 個案例，含經度的 cos 緯度修正
- 座標解析：10 種貼法（純座標對／Google 地圖網址／度分秒／含雜訊／錯誤輸入拒絕）
- 距離判定：5 種情境，誤差折扣邏輯與正式系統一致

### ⚠ 未驗證項目（Eason 2026-08-27 決定不補跑，留到試辦階段暴露）

- **20m 半徑的實地距離判定**——未在店內貼座標實測。
  風險低：判定是純數學且已驗過，GPS 讀數 ±13m 也已知。
- **Android 裝置**——只測了 iOS。Android 的定位行為與 LINE 版本差異未知。
  留到一店試辦時自然暴露。

### 一個已知的取捨（不是缺陷，是現有系統的設計）

±13m 誤差配上折扣邏輯（`有效距離 = 距離 - 誤差`），意味著
**站在門市外約 33 公尺內都會判定為可打卡**。

這是現有系統既有的取捨（寧可放寬，也不要誤擋真的在店裡但定位飄的人）。
GPS 擋得住「在家打卡」，擋不住「人在店門口外面晃」。
真要收緊需配合別的機制（例如店內 QR 碼），不在本階段範圍。

## 後續階段

1. **後端身分層**：userId↔員工對照表、綁定 handler（5 個後端各一份：光復／美村／南昌／央廚／總部）
2. **前端身分層**：`liff.getProfile()` 取代 `?k=` 金鑰；順手補掉「連結轉傳＝薪資外洩」
3. **全門市座標表**：支援打卡時用 GPS 自動標記地點（打卡仍走本店後端，不切換）
4. **manager.html 進 LIFF**：店長不用再保管主管金鑰網址（那條外流比員工的嚴重）
5. **圖文選單**：一個官方帳號，per-user 選單區分店長／同仁
6. **逐日出勤明細分頁**：目前只看得到「今天」，缺整月逐日列表（此項與 LINE 無關，可獨立先做）
